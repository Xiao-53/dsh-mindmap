# dsh-mindmap Constitution

## Core Principles

### I. 内容生成与界面实现职责分离

DSH 的地图生成与修改输出仅限 JSON 知识结构和 Markdown 内容，即 `map.json`
与节点笔记；不得要求模型生成或修改界面 HTML、CSS、布局坐标或 `layout.json`。
插件必须维护完整界面模板，将内容数据填入模板，负责布局计算、连线、动画、导航、
交互、布局持久化及 DSH 侧栏渲染。新图或新增节点缺少布局是合法输入，必须由插件补齐。

原型 `docs/knowledge_atlas_demo_v17.html` 仅供开发插件及开发验收使用，
不得作为 DSH 内容生成的输入或运行依赖。DSH 提示词只包含内容格式、生成与修改规则、
当前任务所需数据及实际可用工具契约，不包含原型源码、角色宣告、目标口号或视觉验收任务。
此分工保证内容局部修改不依赖重新生成整份界面。

### II. 独立数据与稳定身份

地图必须使用 `map.json` 保存知识结构、独立 Markdown 保存详情、`layout.json`
保存插件维护的布局；具体字段遵循 `docs/mindmap-storage-format.md`。
内容修改不得重置已有手动布局，布局调整不得改写知识正文。
地图、节点及关系必须使用稳定身份，改标题不得改变身份；同名新地图不得覆盖已有地图。
共享节点必须复用正文和子图入口，不得因多处显示而复制知识身份。

首次创建地图时，插件必须在当前工作区专用数据目录内建立该地图的独立文件夹；
资源和导出目录按需创建，不生成空笔记或占位目录。结构必须校验身份唯一、引用有效、
视图父级无环；合法知识关系循环不得被误拒。无效数据必须报告具体对象，
不得静默修复后写回；已有有效画面必须保留并标明旧版本。

### III. 用户控制发送与修改保护

加入引用或准备问题只能生成可编辑草稿，必须由用户手动发送。
插件不得自动提交现有草稿，不得因引用操作直接发起模型请求；插入必须保留已有文本、
引用和附件，并绑定原会话，不能向其他会话兜底插入。
引用必须保存可读原文与稳定来源身份；来源变化或失效时保留快照并如实说明，
不得按同名标题猜测目标或假装精确定位。

内容修改必须限定本次目标，保留未涉及的对象与文件，提交前检查实际内容是否已变化；
冲突不得静默覆盖。删除必须区分视图中移除与全图删除，并按已确认的影响范围执行。
多文件变更必须具备完整校验、提交和失败恢复能力；未验证该能力时只提供变更提案，
不得用顺序覆盖冒充完整提交。不得将提示词当作文件校验、并发保护或事务实现。

### IV. 官方契约与最小实现

DSH 接入必须以目标版本的官方 API、文档或源码契约为依据，社区资料不能替代兼容性依据。
必须优先复用官方工具和原生能力，技术选型必须由具体需求与已核实的宿主契约支持。
前端框架、图形库、状态管理及架构细节未确定前，不得以宪章或占位工程预先锁定。

变更必须保持最小必要范围，不生成演示代码、占位组件或无用途目录。
未建立产品工程前，不得添加构建、测试框架、CI 或 Agent 编排系统。
Archify 只作为结构化数据、统一渲染和结构校验的参考，不引入整套 CLI、Viewer 或交付流程。

### V. 一致呈现与可验证交付

插件的动画、排版、节点及已有交互必须按 HTML v17 和已确认产品要求实现与验收，
不得仅保留大致风格后另行设计。内容与视图变化必须保持统一呈现规则；
层级由实际数据决定，不硬编码层数上限，不内置原型示例课程作为产品内容。

每次变更必须执行与范围相称的验证，报告实际结果、未执行项和未解决限制。
宿主接入必须核对目标版本契约；文件写入必须验证数据与失败保护；
界面和导出必须在对应环境验证可用性。规划中的验收目标不得写成已通过结果，
文档变更不得以未运行产品为由引入测试工程。

## 产品与交付边界

- 当前目标宿主为 DSH `v0.2.2-rc.3`，使用原生侧栏接入，Better Sidebar 不是必需依赖。
  目标版本调整时必须重新核查官方兼容性依据并记录结论。
- 产品面向桌面侧栏。输入端点使用雾霾蓝 `#8699aa` 实心圆，输出端点使用灰豆沙
  `#b38c97` 空心圆及 2px 描边；进入和退出子图每次完整过渡均为 0.5 秒，
  无重影或回弹。减少动态效果偏好按产品规范处理。
- 首期与输入框的交互闭环为“选中文本 → 加入输入框 → 点击引用回跳”，由用户自行发送。
  具体阅读、搜索、刷新及后续编辑、工具和分享范围以
  `specs/001-sidebar-knowledge-atlas/spec.md` 为准；完整产品范围不等于当前实施批次。
  新增范围必须先明确需求与分期，不因写入宪章自动排期。
- 工作区数据根目录名称暂定为 `dsh-knowledge-maps/`；路径必须限制在所属地图与
  宿主授权范围内，不能通过绝对路径、路径跳转或符号链接绕过边界。
  Markdown、原始 HTML、脚本及指令性文本不得作为任意代码执行。
- 分享必须导出为可离线阅读的独立 HTML，不提供 JSON 分享导出。
  导出仅包含选定范围的知识内容、必要资源和阅读功能，不包含聊天记录、草稿、
  会话绑定、凭据、本机绝对路径或依赖 DSH 的宿主动作。

## 开发流程与质量门槛

- 使用中文沟通和编写项目文档，保留官方命令、API 和标识符原名。
- 使用 GitHub 官方 Spec Kit，Codex 集成位于 `.agents/skills/speckit-*/SKILL.md`，
  辅助脚本使用 PowerShell（`pwsh`）。宪章建立后，规范、澄清、规划、任务、分析、
  实现均按用户手动调用推进，不自动进入下一步骤，不恢复已撤回的开发顺序。
- 技术规划必须检查宪章、最新功能规范、存储契约和提示词之间的一致性，
  对尚未验证的宿主或写入能力明确标记待验证，不将其当作既有能力。
- 开始与结束工作时必须检查 Git 状态，保留已有用户修改，不自行推送或发布。
  不提交凭据、会话记录和机器本地状态；`.agents/skills/` 与 Spec Kit 配置、模板、
  脚本属于应保留并纳入版本控制的项目内容。
- 已有 `.specify/` 时，必须先运行 `specify integration status`；
  修复或升级使用 `specify integration install codex` 或
  `specify integration upgrade codex`，不得重复运行 `specify init`。
  不为验证工具而生成产品规范或执行实现命令。
- 每次规划、任务分析与变更审查必须核对职责分离、身份与数据保护、手动发送、
  官方兼容性及验证证据。违反宪章的方案必须先修正；需要改变原则时先完成宪章修订。

## Governance

本宪章是项目原则与治理的依据。后续规范、计划和实现必须遵守本宪章；
功能规范负责细化产品范围，存储契约负责细化字段，均不得隐式改变本宪章。
与后续用户明确决定发生冲突时，按用户决定修订宪章并记录影响，不能继续沿用过时原则。

修订必须记录原因、受影响原则、版本变化及对既有规范、数据和实现的影响，
涉及不兼容变更时必须说明迁移或处理方案。修订须经用户明确要求或认可，
不得在普通实现中静默改变原则。宪章更新必须检查相关文档与模板的一致性，
超出当前命令修改范围的同步项只记录，不擅自修改。

版本采用 `MAJOR.MINOR.PATCH`：移除或不兼容地重定义原则提升主版本；
新增原则、章节或实质扩展治理要求提升次版本；不改变含义的措辞与错误修正提升补丁版本。
本次从未填写模板首次采纳为 `1.0.0`，采纳日期保持不变，修订日期随实际修订更新。
每次修订在文件顶部保留临时同步影响报告供审阅，提交前移除该注释。

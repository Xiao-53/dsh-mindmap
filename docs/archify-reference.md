## 最值得借鉴的机制

Archify 的 tree 流程是“结构化 JSON → 校验与布局 → SVG → 统一 HTML 模板”。
HTML 是渲染产物，其输入仍是独立的结构化数据。因此，它与本项目的“稳定画布 + 文件数据”方向一致，不能仅凭最终交付 HTML 就认为它每次重新编写一整页界面。

- **数据与呈现分离**：tree 节点有 `id`、`label`、可选 `parent`、`sublabel`、`collapsed`、`sources`。AI 可以修改节点和关系，统一渲染器负责界面风格。
- **稳定身份**：父子关系引用节点 ID；节点文字和显示位置不承担身份。对本项目，引用回跳也应围绕稳定的导图与节点身份建立，而非只记屏幕坐标或标题。
- **显式结构检查**：拒绝重复 ID、父节点缺失、根节点数量错误及循环关系；不偷偷补接关系。可以借鉴“错误明确报告、保留可修复源文件”的原则。
- **布局规则集中**：节点测量、文本换行、分支间距、连线等由渲染器统一计算，减少 AI 修改内容时反复改样式和手工坐标。
- **阅读位置稳定**：该 tree 实现先为完整树布局，折叠时隐藏后代而不移动剩余节点；可参考其减少阅读跳动的思路。本项目的下钻与返回遵循 HTML v17 和产品规范，不直接采用其折叠策略。
- **隐藏节点可定位**：Finder 或链接选中隐藏节点时，Viewer 会先展开祖先。对本项目可借鉴“点击引用后能找到目标”的行为，不必复制整套搜索和分享功能。

## 应保留的区别

Archify 的 tree 模式表达单根、单父级的包含关系，布局方向为向下或向右；该模式没有跨分支连线。
本项目已要求分层视图、跨视图共享节点及多对多知识关系，不能用单父树替代知识网络；视图父级仍须无环，与允许成环的知识关系分开校验。具体渲染技术尚未选择。

tree schema 的 `sources` 用于来源证据，不是本项目完整的笔记文件绑定、读写和引用回跳协议；不能直接照搬为文件节点模型。
其查看、折叠和导出能力，也不能替代 DSH 的输入框引用 source、发送时序列化及会话绑定。

本项目已在[产品规范](../specs/001-sidebar-knowledge-atlas/spec.md)与[存储契约](mindmap-storage-format.md)中定义选文范围、可读引用快照、稳定地图与节点身份、来源变化后的定位行为及编辑冲突保护；宿主接入与写入机制仍需在技术规划中验证。
普通引用加入草稿时不触发发送，点击引用也只定位来源。

## 对最小实现范围的启发

后续可以围绕“固定呈现规则、独立内容数据、按稳定身份定位”收敛；这里的固定指风格和渲染规则稳定，不是固定像素大小或禁止侧栏响应布局。
已确认用 `map.json` 集中保存结构与摘要，有正文的节点关联独立 Markdown 笔记；没有正文不创建空文件。`layout.json` 由插件独立生成和维护，不属于 DSH 内容输出。

不直接采用 Archify 的完整数据 schema、CLI、HTML Viewer、动画、分享、录制导出或多阶段交付流程，也不因其使用 SVG 就提前决定本项目渲染技术。
借鉴的是数据与渲染分离的原则；文件格式与职责已由存储契约确定，渲染方式和布局算法留待技术规划，不预先指定框架或图形库。
